### <a name="_qmphm5d6rvi3"></a>**Решение**
Приведите диаграммы контекста и контейнеров в модели C4. Опишите там основные компоненты и интеграции всех элементов решения. 

Диаграмма контекста - [context_c4.drawio](context_c4.drawio)

Диаграмма контейнеров - [containers_c4.drawio](containers_c4.drawio)

Также опишите, какой логикой вы руководствовались в ходе принятия решений и выбора технологий. Не забывайте, что необходимо учесть все функциональные и нефункциональные требования.
1. Создан новый сервис депозитов, который отвечает за открытие вкладов, хранение и формирование заявок, передачу заявок на согласование в систему АБС. В качестве платформы разработки был выбран .NET, так как у сотрудников уже есть экспертиза работы с этой технологией.
2. Передача заявок в АБС происходит асинхронно через кафку, сервис АБС вычитывает заявку, которая дальше обрабатывается сотрудником бэк-офиса. 	Очередь может накапливать много заявок, обрабатываться постепенно. Высокая отказоустойчивость - можно временно потерять связь из ИБ с АБС — заявки сохранятся.
3. Как только сотрудник бэк-офиса обрабатывает заявку, АБС также асинхронно уведомляет сервис депозитов, что заявка была согласована/отклонена.
4. Чтобы автоматизировать процесс редактирования ставок, был добавлен сервис ставок, с которым будут работать сотрудники бэк-офиса (депозиты и кредиты). API этого сервиса будет принимать запросы на редактирование ставок, а также рассчитывать персональные ставки для клиентов ИБ.
5. БД в сервисах интернет-банка продолждают работать на MS-SQL, БД АБС использует Oracle. Стараемся сохранить текущие технологии.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

1. Вместо сервиса ставок можно продолжать использовать Excel-файлы и пересылать их по почте между сотрудниками бэк-офиса. Но это замедляет получение актуальных ставок клиентами и создает дополнительную нагрузку на сотрудников.
2. Сервис депозитов может напрямую ходить в АБС для согласования депозита для клиента, но это противоречит требованию избежать прямой зависимости между API АБС и интернет-банком.

**Недостатки, ограничения, риски**
1. АБС по-прежнему можно масштабировать только вертикально. Это создает риски при увеличении кол-ва заявок БД может начать деградировать.
2. Нужно будет переобучить сотрудников бэк-офиса использовать новый сервис ставок вместо ручного заполнения и пересылки Excel-файлов.
3. Нет инструмента контроля за скоростью обработки заявок из очереди. Какие-то заявки могут "зависнуть" в очереди и это создаст негативный пользовательский опыт.
4. В рамках данного ADR не рассматривалась логика работы с SMS-шлюзом.
